# A40 — 2026-09-23: Swift v2 addition partitions

This amendment makes prospective decisions for the 14 A38/A39 additions in
`swift-synthetic-v2`. It preserves all 104 input identities, the prior v1
population and reports, and the two unresolved opaque modeling identities.
It is not a population freeze or a publication decision.

## Result query activation

The independent direct-flow and endpoint-identity controls retained in #229
activate the controlled Result query surface for each tool. Both Result
polarities are selected for execution. Missing flow in the earlier Result
feasibility probes is observed candidate behavior, not an admission failure.
The controls do not certify aggregate memory compliance or analysis
completeness, and the probes do not become scored results.

The new `swift-v2` adapter configuration separates executable Result activation
from native capability decisions. An `active` activation document applies to
`executable_scope: result-language-extension`; it does not assert native
capability. Native unsupported decisions require their own pinned catalog and
declaration evidence.

## Execution contract

The configuration, activation evidence and all 14 case decisions must be
committed before fresh scored attempts. Each tool writes separate native and
Result reports, bound to the full immutable v2 fixture revision. Every native
row belongs to the tool-native modeling profile; every Result row belongs to
the benchmark-controlled language-extension tier. No prior report or adapter
configuration is replaced.

Scored extraction has a 60-second operational cap. Analysis, including query
compilation, has a 60-second cap and requests 512 MiB. No tool-raised minimum,
unknown aggregate memory use, timeout, extraction failure or unproved absence
is converted into a clean negative. The process recorder explicitly does not
prove complete descendant containment and retains scratch directories.
Only compilers and analyzers inspect fixture source; native fixture binaries
are never run.

The newly retained Foundation feasibility extraction used an explicit
180-second diagnostic cap. It completed in about 67 seconds and therefore
cannot be substituted for a scored extraction at 60 seconds. All its raw
artifacts remain non-scored. Finalized databases support structural catalog
and declaration inspection; finalization alone certifies neither memory nor
semantic completeness.

## CodeQL native decision

The pinned shipped command-injection model surface lacks both required A38
native source families: `ProcessInfo.environment` and `CommandLine.arguments`.
The retained full catalog has 876 rows, including 45 source rows. The shipped
non-CSV source implementations cover contents-of initializers, web/JavaScript
entrypoints and application launch URLs; their shapes do not cover these two
source families. `Customizations.qll` adds no models. Finalized diagnostic
extractions resolve the environment and argument declarations at the fixtures'
source anchors. This supports a scoped unsupported decision for all 12 native
cells before scored execution.

This is not a claim that all Swift native models are absent: the catalog has
`Process.run` sink rows, Data summaries and numeric barriers. The diagnostic
databases did not establish a complete static `Process.run` target or an
instantiated shipped sink, so no sink qualification is claimed. The partition
rests on the independently audited missing source requirement. No custom
source, sink, summary or persistence model is introduced.

## Joern native decision

The bounded pinned-distribution audit complements the 58-record vendor query
catalog, which has no Swift query. It inventories the installed JAR classes
and resources and inspects the actual default-semantics implementation and
Swift frontend. Built-in semantics compose operator, C and Java method flows;
the generic loader accepts caller-supplied method mappings. Neither supplies
a shipped Swift-native endpoint catalog for the A38 sources and sink. Swift
parsing and type recovery do not establish native model provenance.

All 12 native cells are therefore prospectively unsupported at Joern 4.0.628.
This decision does not deny the generic API's ability to express mappings or
barriers, and does not claim absence in future releases or external model
packs. No benchmark-authored native semantics are supplied. The exact source,
bytecode, resource inventories and bounded audit remain retained separately
from the scored Result attempts.
