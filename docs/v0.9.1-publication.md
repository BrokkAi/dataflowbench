# v0.9.1 publication runbook

This is the operator runbook for publishing the v0.9.1 Bifrost refresh after
evidence PR #293 has merged. It records the repository workflow; it does not
assert that the matrix, freeze, tag, release, or Pages deployment is complete.
Run it from a separate clean publication checkout; do not reset, switch, or
clean a worktree that is running the matrix.

## Bound release set

Use `reports/releases/v0.9.1/plan.json` as the source of truth. Select exactly
the 92 report paths in the plan:

- the 20 fresh paths in `groups[].reports[].path`; and
- the 72 carried paths in `carried_reports[].path`, preserving their v0.9.0
  provenance and bytes.

The plan expects 1,108 cases and 4,252 rows: 1,116 rows from the fresh groups
and 3,136 carried rows. Every matrix command and population-aware validation
command uses `--population v0.9.0` and the release fixture revision
`sha256:7c8619b2d4a93467fd0a502ed03668bfc8f3b9878a7bd5e9271c7aca31f75f62`.
Do not select reports by directory glob, current working-tree discovery, or a
newer default population.

The strict original Bifrost qualification failed and remains immutable at
`reports/releases/v0.9.1/qualification/attempt-01/qualification.json`. The
separate audited review at
`reports/releases/v0.9.1/qualification/review-01.json` is
`verified-with-known-limits` with `full_policy_qualification: false`. It
supports the measurement workflow only; it is not full policy qualification.
Preserve its typed limitations:

- three JavaScript `partial_discovery` runs remain `inconclusive`;
- 15 complete controls with `empty_selection` advisories are vacuous zero
  findings, not clean negatives; and
- the v0.13.0 native partitions remain `unsupported` because the standalone
  engine has no active product rule packs.

Do not turn any of these outcomes into `not-reached`, omit them from evidence,
or describe the audited review as a clean qualification.

## After evidence PR #293 merges

1. Refresh the repository view and resolve the exact merged evidence commit.
   Require a clean checkout of merged `main`, terminal green CI for the merged
   evidence, and all 20 fresh reports, their raw evidence, receipts, the plan,
   and the 72 carried references at that commit.

   ```bash
   git fetch origin main --tags
   git switch main
   git pull --ff-only origin main
   git status --short
   git rev-parse HEAD
   ```

   Treat the printed commit as the evidence merge SHA only after checking that
   it is the merge result of PR #293. Verify plan paths and digests from that
   commit, for example:

   ```bash
   git show <evidence-merge-sha>:reports/releases/v0.9.1/plan.json
   git show <evidence-merge-sha>:reports/releases/v0.9.1/ledger-v2.jsonl
   git show <evidence-merge-sha>:reports/releases/v0.9.1/qualification/review-01.json
   ```

2. Recheck pin currency before creating a freeze. Compare every declared
   adapter pin with the then-current stable upstream receipt. Record each
   analyzer as `bump`, `hold` with a dated reason, or `current` in the dated
   review and `docs/adapters.md` as required by
   [the freeze-prep policy](freeze.md#freeze-prep-checklist). A bump requires
   a new evidence rerun and a new evidence merge; stop this runbook until that
   evidence is merged.

3. Validate the current receipts against the exact merged tree. Re-read the
   acquisition and upstream receipts under
   `reports/releases/v0.9.1/acquisition/` and
   `reports/releases/v0.9.1/upstream-review.json`, the qualification review,
   `runner-build.json`, every attempt receipt, and every normalized report's
   tool, build, population, fixture, membership, and raw-output digests.
   Reject stale, missing, substituted, or working-tree-only receipts. Keep
   failed and superseded attempts available for audit.

4. Run the repository validators from a clean checkout using the named
   population. These commands are checks, not evidence generation shortcuts:

   ```bash
   cargo run -- --population v0.9.0 validate
   cargo run -- --population v0.9.0 validate-reports
   ```

   The top-level report validator checks legacy normalized reports. Validate
   the nested 92 plan-selected reports and their raw evidence through the
   new freeze as well. Inconclusive, unsupported, runner-error, and incomplete
   outcomes remain typed outcomes.

## Separate freeze and publication PR

The evidence merge and the freeze are separate PRs. A squash merge discards
the evidence branch's commit identity, so never create the release freeze on
the evidence branch before PR #293 merges.

1. From clean merged `main`, run `create-freeze` with one `--report` argument
   for each of the 20 `groups[].reports[].path` entries and each of the 72
   `carried_reports[].path` entries from `plan.json`:

   ```bash
   cargo run -- --population v0.9.0 create-freeze \
     --report <plan fresh report path 1> \
     --report <plan fresh report path 2> \
     ... \
     --report <plan carried report path 1> \
     --report <plan carried report path 2> \
     ... \
     --scope release --release v0.9.1
   ```

   Confirm that the manifest records the surviving merged evidence revision,
   the v0.9.0 population, the stated fixture digest, all 92 reports, and every
   referenced raw-evidence digest. Commit the manifest and generated result
   artifacts in a second, separate freeze/generated-artifacts PR.

2. Commit the manifest on the freeze branch before generating artifacts. Run
   the versioned release checker from that clean commit, passing the surviving
   evidence merge SHA and an absolute reviewed runner path:

   ```bash
   python3 scripts/check-release-v091-results.py \
     --evidence-revision <evidence-merge-sha> \
     --binary <absolute-runner-path> \
     --generate-output <empty-directory-outside-the-disposable-clone>
   ```

   The checker verifies every evidence digest and the exact 20-fresh/72-carried
   freeze. It reuses the existing isolated clone and official remote-main/tag
   checks. Before publication, its temporary local tag exists only inside the
   disposable clone; it is never pushed. Copy the generated artifacts into
   `results/`, commit them, then rerun the checker without `--generate-output`
   to prove the committed files are current. Integrate and test the website's
   archived/current result data using the existing v0.9.0 publication pattern.
   Existing Bifrost v0.12.0 warm/overhead measurements retain their provenance;
   do not relabel them as v0.13.0 measurements.

3. Write `docs/releases/v0.9.1.md` from the fixed template in
   [freeze.md](freeze.md#release-notes-template). Include the freeze identity,
   fresh versus carried report groups, the complete dated pin-currency table,
   honest negatives and typed limitations, bound evidence, reproduction
   commands, and immutability statement. The notes must state that the strict
   qualification failed, the audited review is known-limits measurement
   evidence rather than full qualification, and native coverage remains
   unsupported.

## Pages, tag, and release

The freeze/generated-artifacts PR must be merged and validated before tagging
and publication. The release checker rehearses tag-dependent generation in a disposable clone
before publication. Publish the permanent tag at the exact validated merged
freeze commit, which contains the frozen evidence revision.

After the freeze and generated artifacts pass the final release checks, the
authorized operator may tag and publish:

```bash
git tag -a v0.9.1 <validated-freeze-merged-commit> \
  -m "DataFlowBench v0.9.1"
git push origin v0.9.1
gh release create v0.9.1 \
  --title "DataFlowBench v0.9.1" \
  --notes-file docs/releases/v0.9.1.md
```

Pages is manual through `.github/workflows/pages.yml`. Dispatch it for the
validated release commit, wait for terminal success, and verify the live site
shows v0.9.1 and the bound results. A queued or running workflow is not success.

Check the tag target, GitHub release body, Pages deployment revision, and live
version independently. No merge, tag, release, or publication is implied by
this document or by a locally passing command.
