# v0.8.0 freeze preparation

Started 2026-09-16. This is the preparation record for a new kernel release,
using public Bifrost v0.11.4 and the latest stable releases of the other
candidates at the dated pin-currency cutoff. It is not a completed freeze or
a result publication.

## Population boundary

The input corpus is the complete default population of **1,000 cases**
(**886 core assertions**) at merged `main` commit
`52db1bf46f0880c271b97b0df0f3e1d40d01fc0a`, including the exceptional-flow
and recursive-composition additions since v0.7.1. The exact case and fixture
bytes are recorded in
[`population.json`](../../reports/releases/v0.8.0/population.json).
Do not pass `--population v0.7.0`: that selects the older released population
and excludes the new kernels this minor release is intended to measure.
Changes to case membership or bytes after this cutoff require an explicit
revision of this preparation record before measurements.

Issue #20 consumes the independently reviewed real-project R2 packet. Its six
repositories share analyzer identities and execution infrastructure with this
cycle, but their reports, freeze, and scorecard remain separate from the
1,000-case synthetic kernel population. The completed review does not
establish analyzer results or alter synthetic denominators.

## Pins and execution

The [dated v0.8.0 pin review](v0.8.0-pins.md) records each candidate
and separately versioned rules/query dependency. These forward declarations
supersede the older pins for this planned release only. The existing adapter
READMEs and `docs/adapters.md` are digest-bound by the accepted R2 review
packet; changing them now invalidates `validate` and requires a successor
analyzer-free review before #20 execution. Preserve those bound files. Adapter
Rust code may move to the new runtime identities because it is not packet-bound;
the execution manifest must bind the exact adapter commit. The new cutoff is
recorded here instead of altering reviewed evidence.
[`bifrost-identity.json`](../../reports/releases/v0.8.0/bifrost-identity.json)
records the downloaded public archive, verified checksum, binary checksum,
and observed version banner. `runtime-identities.json` records the other
materialized candidates and the Semgrep 1.177.0 identity mismatch. Private
development builds do not substitute for release assets.

The new [`rerun-plan.json`](../../reports/releases/v0.8.0/rerun-plan.json)
records required slices and evidence groups. Its report rows now contain exact
host-local candidate arguments and reference the digest-bound
[`case-memberships.json`](../../reports/releases/v0.8.0/case-memberships.json),
generated from the 1,000-case population by
`scripts/prepare-v080-execution-plan.py`. The plan remains
`integration-blocked`: resolving command and population ambiguity does not
qualify candidate integration, probes, identities, or timing. Every adapter must be refreshed
against the new population and fixture revision, including unchanged tools.
All attempts, positive/negative controls, raw outputs, normalized reports,
cold sidecars, warm observations, and invocation-overhead repeats must retain
their own identities. Unsupported, inconclusive, runner-error, and incomplete
execution remain distinct; missing evidence does not count as a negative.

The executor, attempt recorder, and progress summarizer now select an explicit
release and keep v0.7.1 backward-compatible. They refuse this blocked plan
until every recorded blocker is resolved, the probe commands are exact, the
runner and artifact identities are collected, and the reviewed plan is marked
executable. Preserve prior release files
in their tagged evidence and preserve every new failed or superseded attempt.
Do not relabel old reports or edit their digests.

Bifrost's 13 kernel commands can use the resumable `run-batch` facility,
with a new manifest under `reports/releases/v0.8.0/`; smoke, modeling,
native, and control probes remain additional required slices. A batch's
completed state does not replace full release validation.

Run measurement processes serially. Qualifying latency measurements require
recorded quiet-host observations; the initial preparation observed CPU use
by background system services, so no timing certification is claimed.

Issue #20 may reuse qualified analyzer identities and these attempt-capture
controls. Its six reviewed repositories, vulnerable/fixed archives, execution
results, freeze, and scorecard remain a separate R2 evidence lifecycle. This
plan does not alter the immutable review packet or count synthetic kernels in
the real-project denominator.

## Delivery gates

1. Land the forward pin declarations and preparation. Resolve the R2 packet
   dependency before changing its bound inputs. Resolve binary, query-pack,
   rules, runtime, and platform dependencies to exact immutable identities.
   Changes to hashed adapter configurations and their fresh reports must land
   together; a declaration alone cannot qualify a report under a new pin.
2. Finalize and check the executable v0.8.0 plan, retaining all fresh and
   failed attempts. Re-run the complete current populations and all required
   controls and latency groups. Resolve adapter capability gaps explicitly.
3. Validate the corpus, reports, exact plan coverage, and evidence inventory;
   merge the resulting evidence PRs. Never suppress configuration drift or
   replace a failed baseline to make the gates pass.
4. From clean merged `main`, create the v0.8.0 manifest in a separate PR.
   Bind every required refreshed report to its surviving evidence commit.
5. Deliberately update the release validation gate and its tests from v0.7.1
   to v0.8.0, then generate and check publication artifacts, write release
   notes, and validate the manifest. Tag/publication follows the validated
   merged manifest; existing tags and release evidence remain immutable.

No v0.8.0 release tag, manifest, score, or timing result is created by this
preparation change.
