# v0.9.2 prospective analyzer execution

`scripts/prepare-release-v092.py` creates a prospective contract at
`reports/releases/v0.9.2/execution-v1/contract.json` from the immutable v0.9.0
execution contract. It requires a complete `group_tools` map, exact tool file
bindings, global `path_replacements`, optional group-specific replacements,
runtime component bindings, explicit source-input digests, a runner-source SHA,
and a fresh resource reservation. It refuses to replace an existing contract
and always writes `execution_authorized: false`; preparation does not run an
analyzer or qualify a tool.

`scripts/execute-release-v092.py` validates and runs a reviewed contract.
Planning mode is read-only:

```sh
python3 scripts/execute-release-v092.py \
  --contract reports/releases/v0.9.2/execution-v1/contract.json
```

Execution requires `execution_authorized: true`, a live resource reservation,
and exact qualification evidence covering each selected group. A selected
`--group` can run while other groups remain pending if its analyzer’s evidence
explicitly covers that group. A full-matrix dispatch checks all 84 group scopes
before launching the first analyzer. The executor does not qualify a tool from
its version string or from an empty report. Qualification evidence binds the
exact analyzer path, SHA-256, version, runtime component identities, and group
IDs it covers. A Bifrost `measurement-with-known-limits` qualification remains
distinct from a strict `qualified` result and is launch-eligible only when its
evidence explicitly says so.

Runtime components are separate digest-bound file entries. CodeQL, Joern,
Semgrep, and Pysa bindings list their underlying engine or runtime files in
`tool_components`; the runner verifies those files alongside the executable.
All CodeQL groups use one `codeql` identity. Regular Java, JavaScript, and
Python commands bind the acquired
`execution-state/v092/tools/codeql-packs` root with `--codeql-packs`. Swift
uses the separately acquired
`execution-state/v092/tools/swift-codeql/candidate-packs-entry2` root because its
6.8.5 custom pack must remain separate from the ordinary pack tree. The Swift
plan binds that absolute root and its exact runtime-tree manifest. Both pack
roots, the CLI, extractor, schema, compiler, and SDK have independent
digest-bound identities.
Explicit `source_inputs` retain only named acquisition and qualification files
needed by the contract. The executor checks those files against the source
commit and copies only those exact files into each fresh source snapshot.
`corpus/` and the registered adapter documentation are also included so the
execution checkout retains corpus metadata and adapter context.

The contract refers to the immutable v0.9.0 plan, execution contract, and
population by path and SHA-256. Validation requires the same 84 group IDs,
exact case memberships, and 92 report partitions, with the selected 1,108 case
IDs covered by the matrix. Groups retain their historical family label while
`tool` names the exact current analyzer identity. Every historical Pysa group
uses one Pysa identity whose component inventory binds the selected Pyre
executable, Pyrefly engine, and Python runtime.

Each execution series creates a new source-only checkout, cache, and evidence
root for every group. Output roots and normalized report sources are relative
to that checkout. A group is launched only while it holds the shared exclusive
analyzer lock, the one-slot resource reservation is live, free disk is at least
125 GiB, and no other heavy build or analyzer process is active. The runner
checks the global wall-time budget before each group and stops when a group
fails, times out, or cannot be recorded. It does not retry automatically. A
reviewed retry retains the same committed contract and series, with a fresh
`attempt-NN` execution/cache root and a separate append-only receipt. The
registered two-attempt ceiling remains in force; completed groups are verified
and skipped on resume. Failed attempts remain in the ledger and are excluded
from report promotion. Resume retains the wall-clock ceiling measured from the
series's first attempt, including pauses; it never grants a fresh total budget.

Timeout and capacity stops track observed descendants by PID and process-start
identity, including children that create separate sessions. Cleanup rechecks
those identities before each signal, verifies that tracked processes stopped,
and retains its signals and any uncertainty in `process_ownership`. A tracking
or cleanup error stops the matrix without promoting reports. Polling does not
prove complete descendant containment; that state stays `unproven` even when
all observed processes have stopped.

The child environment is explicit. Bifrost groups set
`BIFROST_OPEN_PACKS_DISABLE=1` to retain the registered benchmark profile.
Semgrep groups place the selected virtual environment’s `bin` directory first
in `PATH`, so a system Semgrep installation cannot take precedence.

Pysa groups use a task-owned external `TMPDIR` at
`/private/tmp/dfb-v092-pysa-<execution-root-sha256-prefix>`. This keeps
Pyrefly 1.4’s scratch files outside the repository’s ignored
`execution-state/` tree. The executor creates that exact directory fresh and
fails if it already exists; the same 24 GiB scratch ceiling and 40 GiB free
space reserve apply while the analyzer runs. The separately captured Pysa
profile control uses a similarly hash-scoped `/private/tmp/dfb-v092-profile-*`
directory and refuses to reuse an existing one.

The attempt receipt keeps the exact command, effective child environment,
source commit, analyzer binding, runtime components, qualification scope,
stdout, stderr, and a digest inventory of every file under the declared output
roots. The original normalized report bytes and all raw files remain in that
attempt’s capture tree. The staged report is a projection of those original
bytes that changes only each result row’s `raw_output` path to the retained
capture path. It leaves outcomes, diagnostics, and typed states such as
`incomplete`, `budget-exhausted`, `cancelled`, `unsupported`, and
`workspace-not-ready` intact. A zero exit code means only that the group
execution and report recording completed; it does not turn an inconclusive or
incomplete result into a clean result.

For example, execute one reviewed group with:

```sh
python3 scripts/execute-release-v092.py \
  --contract reports/releases/v0.9.2/execution-v1/contract.json \
  --group codeql-swift-common108 \
  --execute
```

Omitting `--group` runs the contract’s 84 groups serially, but only after all
84 groups have eligible qualification coverage. Each group’s status and
attempt ID are printed as the matrix proceeds. Captured attempts and projected
reports are stored under `reports/releases/v0.9.2/attempts/` and
`reports/releases/v0.9.2/normal/attempts/`; the append-only ledger is
`reports/releases/v0.9.2/ledger-v1.jsonl`.

## Fresh Swift qualification

The pending executable plan templates are under
`execution-state/v092/plan-templates/`. They preserve the common-1,108 and
Swift-108 projections. They are not executable while any runtime, query,
control, or projection field remains marked pending. The generated executable
plans live at `adapters/codeql/swift-common-v2/plan-v092-01/execution-plan.json`
and `adapters/joern/swift-common-v2/plan-v092-01/execution-plan.json`; each
binds a separately reviewed control plan and a fresh qualification receipt.

For CodeQL, the scored common-108 query root is the versioned nested profile at
`adapters/codeql/v0.9.2/swift/queries/`. Its standard, opaque, and native
directories preserve the existing 12-query closure. Qualification compiles
and resolves those 12 queries with the newly built 2.27.2 CLI, Swift 6.8.5
extractor, and `6.8.5-dfb.entry2` pack. A separate entrypoint control set
retains all ten registered positive and negative fixtures. Two model controls
compare production `kernel-flow.ql` with production `modeling-flow.ql`; four
sanitizer controls compare production modeling with a separately retained
control query that removes only `sanitizer(n)` from the barrier predicate and
keeps `summaryBarrier(n)`. The counterfactual patch and both query files are
digest-bound. The entrypoint results may retain the known array-element
negative and callback-registration positive limitations as
`measurement-with-known-limits`; they do not become strict passes. A typed
incomplete extraction, failed command, timeout, or cleanup uncertainty blocks
eligibility and remains in the raw capture.

The guarded CodeQL query preflight and control capture are separate append-only
records. The retained query check is `query-check-02`; all 12 nested
common-108 queries resolved and compiled with the exact 2.27.2 runtime. The
fresh control capture is `control-attempt-02`: its ten entry controls, four
model arms, and eight sanitizer arms completed, and all raw tables and command
records were replayed. The capture recorder failed after the raw evidence was
complete because it compared an assessment before placing that assessment in
the run record. The separate `control-replay-02a` receipt reconstructs the run
record and independently replays the retained evidence without rerunning
CodeQL. Entry results remain `measurement-with-known-limits` because the
array-element negative and callback-registration positive controls differ
from expectation; the model and sanitizer dimensions pass their strict
controls. These limits remain visible in the receipt, and activation remains
unscored.

The current CodeQL plan is execution-eligible with that receipt. The
pre-promotion plan bytes are retained beside the recovery receipt and bound to
the original capture-index digest. The guarded commands used for the fresh
query check and controls were:

```sh
DATAFLOWBENCH_V092_QUALIFICATION=1 \
DATAFLOWBENCH_V092_GROUP_ID=codeql-swift-common108 \
python3 scripts/run-swift-common-v092.py check-queries \
  --plan adapters/codeql/swift-common-v2/plan-v092-01/execution-plan.json \
  --output reports/releases/v0.9.2/qualification/codeql-swift-common108/query-check-02

DATAFLOWBENCH_V092_QUALIFICATION=1 \
DATAFLOWBENCH_V092_GROUP_ID=codeql-swift-common108 \
python3 scripts/capture-codeql-swift-controls-v092.py \
  --plan adapters/codeql/swift-common-v2/plan-v092-01/execution-plan.json \
  --control-plan reports/releases/v0.9.2/qualification/codeql-swift-common108/control-plan-02.json \
  --query-receipt reports/releases/v0.9.2/qualification/codeql-swift-common108/query-check-02/receipt.json \
  --output reports/releases/v0.9.2/qualification/codeql-swift-common108/control-attempt-02
```

The capture uses 150 seconds for extraction, a shared 75-second analysis
budget per control, a 5,400-second total ceiling, a 4 GiB scratch allowance,
and a 40 GiB free-space reserve. It does not launch the scored 108-case
matrix.

The CodeQL v0.9.2 report boundary replays the fresh compile-only query receipt
for the run and requires the exact same path/SHA in every raw case record. It
rejects query revalidation metadata before delegating the report projection to
the unchanged v0.9.1 exporter. Qualification commands and their source, query,
fixture, and output paths stay bound to the original capture root. Replay on
this host also requires that original capture root to remain available; each
fresh release snapshot carries byte-identical copies at the same relative
paths. The source-input collector binds exactly the 34 captured Swift source
files used by the controls and the archived pre-promotion plan, without
copying database or cache trees.

The complete digest-checked acquisition and qualification closure is generated
by `scripts/collect-v092-source-inputs.py` and retained at
`reports/releases/v0.9.2/qualification/source-input-closure-01.json`. It lists
727 explicit files, including 14 acquisition inputs, 655 qualification
evidence files, the 34 CodeQL captured Swift sources, and 24 digest-bound
native CPG files totaling 1,338,276 bytes. The collector follows only paths
named by the executable plans and their evidence; it does not walk output
directories or include analyzer databases and caches. The host-bound
`scripts/test-replay-codeql-swift-controls-v092.py` integration checks require
the retained acquisition and original capture root, so they are run locally
and are not hermetic CI tests.

Joern’s fresh controls preserve six fixtures, each with modeling off and on,
for 12 case-arms and at most 36 phase invocations. Attempt04 completed all 36
typecheck, frontend, and query phases within the existing 75-second arm and
900-second total limits, with the 4 GiB scratch cap and 40 GiB reserve. Four
direct arms passed. The exact strict model assessment remains `incomplete`
with eight typed `Incomplete:EndpointIdentity` opaque arms; the diagnostic
review independently replayed their captured CPG declarations, wrapper
identities, and external call edges. Its receipt is
`control-attempt-04/qualification-receipt-02.json`, status
`measurement-with-known-limits`, with full model qualification and scored
activation both false. Attempt03’s pre-arm process-cleanup failure remains
preserved and is not treated as a control result.

The diagnostic receipt authorizes bounded execution while retaining the

the exact source or sink identity. This admission does not establish full
model activation, aggregate resource qualification, or complete absence
analysis. Runtime inventories consumed by these versioned runners use the
legacy runner’s explicit `manifests` map for CodeQL and `inventories` map for
Joern; the newer acquisition inventory envelope is not passed directly into
those verifiers.

## Final evidence gates

After all 84 groups complete, run `scripts/check-release-v092.py` to verify
92 fresh report partitions and 4,252 rows on the unchanged 1,108-case
population. Its summary retains failed attempts separately and never promotes
partial reports. Native configuration hashes that cannot be reconstructed
from repository inputs remain explicitly `NotDerivable`.

Then run the separate canonical Rust configuration gate:

```sh
python3 scripts/validate-v092-report-configurations.py \
  --contract reports/releases/v0.9.2/execution-v1/contract.json \
  --output configuration-validation-01 --execute
```

It creates a fresh source checkout from the measured source commit, projects
only the 92 verified reports and their referenced raw files, and runs the
exact pinned harness with `--population v0.9.0 validate-reports`. The
append-only receipt is saved under
`reports/releases/v0.9.2/validation/configuration-validation-01/`. Success
requires 92 validated reports and zero known-stale configurations; the number
of independently derivable configuration hashes is recorded separately.
Evidence delivery requires both gates. Freeze creation still follows the
repository's separate clean merged-main workflow.
